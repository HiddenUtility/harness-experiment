# AGENTS.md

## 1. 基本ルール
- 日本語で会話してください。
- 既存のコードやディレクトリ構成を尊重してください。
- ユーザーの指示を最優先してください。
- 曖昧な仕様は勝手に決めず、必ずユーザーに確認してください。

## 2. プロジェクト概要
- **プロジェクト名**: `go-utils`
- **目的**: さまざまなGoプロジェクトで使い回せる汎用的なユーティリティ集（IO操作、ネットワーク、セキュリティ等）の提供。

## 3. 技術スタック
- **言語**: Go (最新バージョン)
- **モジュールパス**: `github.com/username/go-utils`
- **外部ライブラリ**: 標準ライブラリをメインとし、実用性が高くMITライセンスのメジャーなライブラリは使用可。

## 4. リポジトリ構成
- `pkg/` ディレクトリ配下にジャンルごとのパッケージを配置する。
  - 例: `pkg/io`, `pkg/net`, `pkg/security`

## 5. アーキテクチャ方針
- 各パッケージは、そのジャンルに関する単一責任の原則に基づいたユーティリティを提供する。
- パッケージ間の依存関係は最小限に抑える。

## 6. コーディング規約
- **命名規則**: Goの標準的な命名規則（PascalCase, camelCase）に従う。
- **フォーマット**: `go fmt` を使用してコードを整形する。
- **ドキュメント**: コード内のコメントおよびGoDocは**日本語**で記述する。

## 7. エラー処理方針
- 標準的な `if err != nil` 形式を使用する。
- 独自のカスタムエラーが必要な場合は、標準的な方法で実装する。

## 8. テスト方針
- Go標準の `testing` パッケージを使用して、各パッケージに対して単体テストを作成する。
- テストファイルは `*_test.go` とする。
- 新しい機能を追加した際は、必ず対応するテストを追加すること。

## 9. 品質ガード
- **静的解析**: `golangci-lint` を使用してコードをチェックする。
- **フォーマットチェック**: `go fmt` を使用する。
- **テスト実行**: コード変更後は必ずテストを実行し、パスすることを確認する。

## 10. CI/CD
- **プラットフォーム**: GitHub Actions
- **実行内容**: プルリクエストおよび `dev` ブランチへのマージ時に、テストおよび静的解析を実行する。

## 11. Git 運用ルール
- **ブランチ戦略**: GitHub Flow をベースに `dev` ブランチを使用する。
- **ブランチの流れ**:
  1. `dev` から `feature/<task-name>` ブランチを作成して作業を開始する。
  2. 作業完了後、`feature/<task-name>` から `dev` へプルリクエストを作成する。
  3. `feature` → `dev` へのマージは AI エージェントが自律的に行える。
  4. `dev` → `main` へのマージは人間が確認した後に実施する。
- **コミットメッセージ**: 意味のある、簡潔なメッセージを記述する。

## 12. AI エージェント運用
- **自律性**: `feature` から `dev` へのマージ作業は、テストとリンターがパスしていることを確認した上で、AI エージェントが自律的に実行してよい。
- **承認**: 基本的に自動で進めるが、重要な変更や構造に関わる変更については、ユーザーに報告する。

## 13. スキル運用
- プロジェクト固有のスキル（`init-project`, `bugfix`, `retro` 等）が定義されている場合は、それらを適切に活用する。

## 14. ドキュメント方針
- 公開される API のドキュメントは、日本語でわかりやすく記述する。

## 15. 禁止事項
- 標準ライブラリ以外のライセンスが不明な、あるいは MIT 以外のライセンスのライブラリを勝手に追加しない。
- `pkg/` 以外の場所に関係のないファイルを大量に作成しない。
- テストが失敗している状態で `dev` ブランチにマージしない。

## 16. 作業完了条件
- 実装した機能が、対応する単体テストによって検証されていること。
- `golangci-lint` がパスしていること。
- `go fmt` が適用されていること。
- `dev` ブランチへのマージが完了していること。
