# Init Project

## 1. 目的

ユーザーとの対話を通じて新規ソフトウェアプロジェクトの要件を収集し、プロジェクトの初期開発基盤を構築する。

プロジェクトの特性とユーザーが承認した仕様に基づき、以下を作成する。

1. `AGENTS.md`：AI エージェント向けの開発指示書
2. `README.md`：人間向けのプロジェクト説明書
3. ディレクトリ構成：ソースコード、テスト、ドキュメントなどの配置
4. `scripts/`：開発・品質チェック用スクリプト
5. CI/CD 設定：GitHub Actions などの自動化設定
6. その他のプロジェクト初期設定ファイル：技術スタックに必要なものに限る

このスキルは、プロジェクトの初期開発環境を構築することを目的とする。

アプリケーション本体の機能実装、業務ロジックの実装、実際の本番環境へのデプロイは行わない。

ユーザーが明示的に依頼した場合を除き、これらの作業は別のタスクとして扱う。

---

# 2. 基本原則

以下の原則を必ず守る。

## 2.1. 要件に関する原則

1. ユーザーが決定した仕様を最優先する。
2. ユーザーが決定していない仕様を勝手に追加しない。
3. 不明点を推測で確定しない。
4. 技術選定を委任された場合は、推奨案と理由を提示する。
5. プロジェクトに不要な機能や設定を追加しない。
6. 将来の拡張予定と現在必要な機能を区別する。

## 2.2. 成果物に関する原則

1. すべての成果物を同じプロジェクト仕様に基づいて作成する。
2. AGENTS.md、README.md、スクリプト、CI/CD 設定の内容を一致させる。
3. 存在しないファイルやコマンドを前提とした指示を記述しない。
4. 実際に動作するスクリプトを作成する。
5. 実際に使用する CI/CD 設定だけを作成する。
6. 不要な依存関係を追加しない。
7. 既存ファイルを無断で上書き・削除しない。
8. ユーザーの既存作業を破壊しない。

## 2.3. AI エージェント向け記述原則

小規模なモデルでも誤解しにくい成果物を作成する。

1. 曖昧な表現を使用しない。
2. 1つのルールには原則として1つの指示だけを書く。
3. 実行条件を明確にする。
4. 判断基準を明確にする。
5. 禁止事項を具体的に記述する。
6. 手順を実行順に記述する。
7. 例外条件を明示する。
8. ルール同士の矛盾をなくす。
9. 不要な説明と重複を減らす。
10. 必要な知識や技術的な背景を明示する。

# 3. 実行フェーズ

以下の6つのフェーズを必ず順番に実行する。

| Phase | 内容 | 成果 |
|---|---|---|
| 1 | 要件ヒアリング | プロジェクト要件 |
| 2 | 要件整理・確認 | 確定したプロジェクト仕様 |
| 3 | プロジェクト構成設計 | ファイル・ディレクトリ設計 |
| 4 | 開発基盤の構築 | 各種ファイル・スクリプト・CI/CD |
| 5 | 整合性検証 | 検証済み開発基盤 |
| 6 | 完了報告 | 構築結果と検証結果 |

各フェーズの終了条件を満たすまで、次のフェーズへ進まない。

# Phase 1: 要件ヒアリング

## 4. ヒアリングの進め方

ユーザーとの会話を通じて、プロジェクトの要件を収集する。

### 4.1. 質問ルール

1. 最初にプロジェクトの目的と完成イメージを質問する。
2. 一度に大量の質問を提示しない。
3. 原則として1回の発言で1つのテーマを扱う。
4. 独立した質問をまとめた方が回答しやすい場合は、複数質問してよい。
5. 回答済みの項目を再質問しない。
6. 曖昧な回答には具体例を示して確認する。
7. 技術的な選択肢にはメリットとデメリットを付ける。
8. 技術選定を委任された場合は推奨案を提示する。
9. プロジェクトに関係しない質問は省略する。
10. 質問は自然な会話形式にする。

質問票を一度にすべて提示してはいけない。

## 5. ヒアリング項目

以下の項目から、プロジェクトに必要な情報を収集する。

### 5.1. プロジェクト概要

- プロジェクト名
- プロジェクトの目的
- 解決したい問題
- 主な利用者
- 提供する機能
- 完成イメージ
- モノレポまたは単一プロジェクト
- 将来的な拡張方針
- オープンソースまたは非公開
- ライセンス

### 5.2. 技術スタック

- プログラミング言語
- 言語のバージョン
- フレームワーク
- ビルドツール
- パッケージ管理
- 対応 OS
- 対応プラットフォーム
- 外部ライブラリの利用方針
- 使用する開発ツール

技術選定を行う場合は、以下を考慮する。

- 保守状況
- 利用実績
- ライセンス
- 安全性
- パフォーマンス
- 開発効率
- 依存関係の数
- 将来的な保守性

ユーザーがライブラリの選定を委任した場合、原則として保守されている実績のあるライブラリを優先する。

ユーザーが指定していない不要な依存関係を追加しない。

### 5.3. アーキテクチャ

- ディレクトリ構成
- モジュール・パッケージの分割方針
- コンポーネント間の依存関係
- 公開 API の設計方針
- エラー処理方針
- 設定管理方針
- データ管理方針
- セキュリティ方針
- 拡張性の方針

### 5.4. コーディング規約

- 命名規則
- フォーマット
- コメント・ドキュメントの言語
- 型の扱い
- エラー処理
- ログ出力
- 非同期処理
- パフォーマンス方針
- 禁止する実装パターン

### 5.5. テストと品質管理

- テストフレームワーク
- テストの種類
- テストの実行方法
- 静的解析ツール
- Linter
- Formatter
- ビルドチェック
- 品質チェックの実行タイミング
- CI で実行するチェック
- テストカバレッジの要否
- 品質チェックの失敗時の扱い

### 5.6. CI/CD と自動化

- CI/CD プラットフォーム
- CI の実行条件
- 対象ブランチ
- Pull Request 時のチェック
- Push 時のチェック
- 自動テスト
- 自動リリースの有無
- デプロイの有無
- 自動化スクリプト
- AI エージェントの自動実行方針

GitHub Actions を使用する場合は、以下も確認する。

- Workflow の分割方針
- 対応 OS
- 使用するランナー
- 対応する言語バージョン
- キャッシュの使用方針
- 並列実行の要否
- 必要な権限

### 5.7. Git 運用

- ブランチ戦略
- ブランチ命名規則
- コミットメッセージ規約
- Pull Request の作成ルール
- レビュー担当者
- マージ条件
- マージ方式
- AI エージェントに許可する Git 操作
- 人間による承認が必要な操作

### 5.8. AI エージェント運用

- 使用する AI エージェント
- AI エージェントの役割
- スキル定義形式
- スキルの配置場所
- スキル間の依存関係
- スキルの自動実行条件
- AI に許可する操作
- AI に禁止する操作
- 人間への確認が必要な条件
- 自動化する範囲
- AI による自己改善の方針

### 5.9. ドキュメント

- README の記載内容
- API ドキュメント
- 設計ドキュメント
- 開発者向けドキュメント
- ドキュメントの更新条件
- ドキュメントの言語
- ライセンス表記

# Phase 2: 要件整理・確認

## 6. 要件の整理

ヒアリング終了後、収集した情報を整理する。

次の形式でユーザーに提示する。

### Project Specification

| 項目 | 決定内容 |
|---|---|
| プロジェクト名 | |
| プロジェクトの目的 | |
| プロジェクトの種類 | |
| 技術スタック | |
| アーキテクチャ | |
| ディレクトリ構成方針 | |
| コーディング規約 | |
| テスト方針 | |
| 品質管理 | |
| CI/CD | |
| Git 運用 | |
| AI エージェント運用 | |
| README 方針 | |
| ドキュメント方針 | |

### 未決定事項

決定していない項目を列挙する。

### 推奨事項

技術的な観点から推奨する設定があれば、理由とともに提示する。

### 矛盾チェック

以下を確認する。

- 技術スタックと開発規約が矛盾していないか。
- アーキテクチャとディレクトリ構成が整合しているか。
- テスト方針と品質チェックが整合しているか。
- CI のチェック内容とマージ条件が整合しているか。
- Git 運用と AI の権限が矛盾していないか。
- 自動化方針と承認フローが矛盾していないか。
- README に記載する内容を実際に提供できるか。

## 7. ユーザー確認

整理した仕様をユーザーに提示し、確認を求める。

ユーザーから修正があれば仕様に反映する。

ユーザーの確認を得る前に Phase 3 へ進んではいけない。

# Phase 3: プロジェクト構成設計

## 8. 既存リポジトリの調査

構成設計の前に、リポジトリの状態を確認する。

確認対象：

- リポジトリのルート
- 既存の AGENTS.md
- 既存の README.md
- 既存のソースコード
- 既存のテスト
- 既存のディレクトリ構成
- Cargo.toml、package.json、go.mod などの設定ファイル
- 既存の scripts/
- 既存の CI/CD 設定
- 既存の開発規約

既存の設定がある場合は、その内容を確認してから設計する。

既存のファイルやディレクトリを削除・移動する必要がある場合は、事前にユーザーの承認を得る。

## 9. ディレクトリ構成の設計

プロジェクトの技術スタック、規模、アーキテクチャに適したディレクトリ構成を設計する。

### 9.1. 設計原則

1. プロジェクトの規模に対して過剰な階層を作らない。
2. 役割が異なるファイルを同じディレクトリに混在させない。
3. ソースコードとテストコードを明確に区別する。
4. ビルド生成物とソースコードを区別する。
5. 設定ファイルの配置場所を統一する。
6. ドキュメントの配置場所を統一する。
7. スクリプトの配置場所を統一する。
8. 技術スタック固有の標準構成を優先する。
9. 将来必要になるかもしれないだけの空ディレクトリを作らない。
10. ユーザーが指定した構成を優先する。

### 9.2. 基本構成例

以下は構成の参考例であり、すべてのプロジェクトに適用するテンプレートではない。

```text
project-root/
├── AGENTS.md
├── README.md
├── LICENSE
├── .gitignore
├── .editorconfig
├── scripts/
│   ├── test.sh
│   ├── lint.sh
│   ├── format.sh
│   └── check.sh
├── docs/
├── src/
├── tests/
└── .github/
    └── workflows/
        └── ci.yml
```

実際の構成は技術スタックに応じて変更する。

例えば Rust プロジェクトでは `Cargo.toml`、Go プロジェクトでは `go.mod`、Node.js プロジェクトでは `package.json` をルートに配置する。

### 9.3. ディレクトリ設計の提示

ファイルを作成する前に、次の情報をユーザーに提示する。

- ディレクトリツリー
- 各ディレクトリの役割
- 各設定ファイルの役割
- scripts に用意するコマンド
- CI/CD Workflow の構成

ユーザーの承認を得てから Phase 4 に進む。

# Phase 4: 開発基盤の構築

## 10. 構築対象

ユーザーが承認した仕様に基づき、以下の成果物を作成する。

### 10.1. AGENTS.md

AI エージェントがプロジェクトで作業する際の行動規則を定義する。

基本構成：

1. 基本ルール
2. プロジェクト概要
3. 技術スタック
4. リポジトリ構成
5. アーキテクチャ方針
6. コーディング規約
7. エラー処理方針
8. テスト方針
9. 品質ガード
10. CI/CD
11. Git 運用ルール
12. AI エージェント運用
13. スキル運用
14. ドキュメント方針
15. 禁止事項
16. 作業完了条件

必要な項目だけを採用する。

AGENTS.md には実際のプロジェクトで使用するルールだけを記述する。

### 10.2. README.md

人間がプロジェクトの目的、利用方法、開発方法を理解できるように作成する。

基本構成：

1. プロジェクト名
2. プロジェクト概要
3. 主な機能
4. 技術スタック
5. 必要な環境
6. インストール方法
7. ビルド方法
8. 実行方法
9. テスト方法
10. 品質チェック方法
11. ディレクトリ構成
12. 開発への参加方法
13. ライセンス

必要な項目だけを採用する。

README.md に記載するコマンドは、実際に実行できるものに限定する。

まだ実装されていない機能を、実装済みとして説明してはいけない。

初期段階で実行できない項目は、未実装または未設定であることを明記するか、省略する。

README.md から AGENTS.md を参照できるようにする。

### 10.3. ディレクトリと設定ファイル

Phase 3 で承認された構成を作成する。

必要に応じて以下のファイルを作成する。

- .gitignore
- .editorconfig
- 言語固有の設定ファイル
- パッケージ管理設定
- ビルド設定
- テスト設定
- Linter 設定
- Formatter 設定
- ライセンスファイル

設定ファイルの内容は技術スタックに合わせる。

既存の設定ファイルがある場合は、その内容を確認する。

既存設定を変更する場合は、変更理由と影響を明確にする。

### 10.4. scripts/

開発作業と品質チェックを簡単に実行できるスクリプトを作成する。

原則として `scripts/` ディレクトリに配置する。

プロジェクトの OS と実行環境に適した形式を使用する。

Unix 系環境ではシェルスクリプト、Windows 環境では PowerShell スクリプトなどを選択する。

必要に応じて複数の OS に対応する。

#### 基本スクリプト

| ファイル | 役割 |
|---|---|
| test.sh | テスト実行 |
| lint.sh | 静的解析・Lint 実行 |
| format.sh | コードフォーマット |
| check.sh | 品質チェックの一括実行 |

プロジェクトに必要なスクリプトだけを作成する。

ビルドが必要なプロジェクトでは build.sh を追加してよい。

#### スクリプトの実装ルール

1. 実際に使用するツールのコマンドを実装する。
2. 存在しないツールを呼び出さない。
3. 必要なツールがインストールされていない場合はエラーメッセージを出力する。
4. コマンドが失敗した場合は非ゼロの終了コードを返す。
5. エラーを無視して処理を継続しない。
6. 実行する処理をユーザーが理解できるように表示する。
7. スクリプトの実行対象を明確にする。
8. プロジェクトルートから実行できるようにする。
9. 作業ディレクトリに依存しないようにする。
10. 必要な実行権限を設定する。
11. フォーマットスクリプトの動作を明確にする。
12. チェックスクリプトは品質チェックをまとめて実行する。

#### format.sh の注意事項

フォーマットスクリプトは、ファイルを書き換える処理として実装する。

CI でフォーマットの検証を行う場合は、書き換えを行わないチェックモードを使用する。

例えば以下のように区別する。

- ローカル：フォーマットを適用する。
- CI：フォーマットが適用済みか確認する。

#### check.sh の実行順序

原則として次の順序で実行する。

1. フォーマットチェック
2. Lint
3. テスト
4. ビルドチェック

ただし、技術スタックに適した順序がある場合は変更してよい。

いずれかの処理が失敗した場合は、check.sh 全体を失敗として終了する。

#### スクリプトの独立性

各スクリプトは単独で実行できるようにする。

他のスクリプトを呼び出す場合は、呼び出し先の終了コードを正しく引き継ぐ。

### 10.5. GitHub Actions

GitHub Actions を使用する場合は、`.github/workflows/` に Workflow を作成する。

基本的には CI 用の Workflow を最低1つ作成する。

例：

```text
.github/
└── workflows/
    ├── ci.yml
    └── release.yml
```

`release.yml` は自動リリースが必要な場合に限り作成する。

#### CI Workflow の基本要件

1. 指定されたブランチへの Push で実行する。
2. Pull Request で実行する。
3. 必要なランタイムとツールをセットアップする。
4. 依存関係をインストールする。
5. フォーマットチェックを実行する。
6. Lint を実行する。
7. テストを実行する。
8. ビルドチェックを実行する。
9. 失敗した場合は Workflow を失敗として終了する。

実際のチェック項目はプロジェクトの仕様に合わせる。

#### CI と scripts の整合性

CI とローカル環境で異なる品質チェックを定義しないことを原則とする。

可能な場合は CI から `scripts/check.sh` を実行する。

CI 固有のセットアップ処理とローカル品質チェックを分離する。

CI で必要な依存関係のインストールやランタイムのセットアップは Workflow 側で行う。

#### GitHub Actions の安全性

1. `permissions` は必要最小限にする。
2. 不要な書き込み権限を付与しない。
3. Action のバージョンを明示する。
4. シークレットをソースコードや Workflow に直接記述しない。
5. ユーザーが指定していない外部サービスを利用しない。
6. 自動デプロイを勝手に有効にしない。
7. リリース処理はユーザーが承認した場合だけ作成する。
8. 未設定のシークレットや環境変数を使用する場合は、必要な設定名と設定方法を README に記載する。

GitHub Actions の Workflow は、実際に利用できる設定ファイルとして作成する。

単なる説明用の YAML を配置して完了としてはいけない。

### 10.6. その他の初期設定

必要に応じて以下を作成する。

- LICENSE
- .gitignore
- .editorconfig
- .gitattributes
- Dependabot 設定
- セキュリティ関連設定
- 開発環境設定
- コンテナ設定

ただし、ユーザーが承認していない機能や外部サービスを追加しない。

## 11. AGENTS.md の記述ルール

### 11.1. ルールの記述形式

各ルールには必要に応じて以下を含める。

- 対象：どのファイル・作業・機能に適用するか。
- 指示：何を実行するか。
- 条件：いつ実行するか。
- 例外：実行しなくてもよい条件。
- 検証：どのように確認するか。

### 11.2. 曖昧な表現の禁止

悪い例：

- テストを適切に実施する。
- 必要に応じてリファクタリングする。
- コードの品質を高める。
- なるべく安全に実装する。

良い例：

- Rust のソースコードを変更した場合、変更したクレートのテストを実行する。
- 最終確認では `scripts/check.sh` を実行する。
- テストに失敗した場合は原因を調査して修正する。
- テストを実行できない場合は理由を作業報告に記載する。

### 11.3. その他の記述ルール

- 1つの箇条書きには原則1つの指示を書く。
- 禁止事項には禁止する具体的な操作を書く。
- コマンドはコードブロックで記載する。
- 手順は番号付きリストで記載する。
- 条件分岐は「〜の場合」と明示する。
- ルールの優先順位を定義する。
- AI が自律的に判断してよい範囲を明確にする。
- 実際に使用するコマンドだけを記載する。
- 存在しないスクリプトや設定を前提にしない。
- 将来の予定と現在のルールを区別する。


実行していない検証を成功として報告してはいけない。

# 17. 安全性と変更管理

以下を必ず守る。

1. 既存ファイルを確認せずに上書きしない。
2. 既存ファイルの削除を勝手に行わない。
3. 既存ディレクトリの移動を勝手に行わない。
4. ユーザーの未コミット変更を破壊しない。
5. 既存の設定ファイルを無断で置き換えない。
6. 既存の CI/CD 設定を無断で変更しない。
7. ユーザーが承認していない外部サービスを追加しない。
8. ユーザーが承認していない依存関係を追加しない。
9. 不要なアプリケーション実装を行わない。
10. Git のコミット、Push、PR 作成を勝手に実行しない。
11. 本番環境へのデプロイを勝手に実行しない。
12. 認証情報や秘密情報をファイルに直接記述しない。

既存ファイルを変更する必要がある場合は、変更対象と変更内容をユーザーに説明し、承認を得る。

新規作成するファイルについても、構成設計の段階でユーザーに提示した範囲を超える場合は追加承認を得る。

# 19. 禁止事項

以下の行為を禁止する。

- 最初の応答でファイルを作成すること。

- 存在しないコマンドを README に記載すること。
- 実行していないテストを成功として報告すること。
- 必要性を説明できない依存関係を追加すること。
- 不要な抽象化や過剰なディレクトリ階層を導入すること。
- 未承認の外部サービスを導入すること。
- 未承認のデプロイ設定を追加すること。
- アプリケーション本体の機能実装を行うこと。
- ユーザーの既存作業を破壊すること。
